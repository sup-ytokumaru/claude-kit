# skill-new

ck のスキルを**新規作成・改訂する**ためのメタスキル。claude-kit の 2 ファイル構成と `ck skill doctor` の規約に沿って、再利用できる形の手順書を書く。

**位置づけ**: `/doc-this` がプロジェクト固有の知見を `.claude/docs/` に残すのに対し、本スキルは**プロジェクトをまたいで使える手順**を ck 本体のスキルにする。判断が要らない機械的な制約は、スキルではなく `doctor` の検査に落とす。

**コア原則: スキルは「一度こう解いた」という物語ではなく、次に同じ状況に出会った人が従える手順である。**

## 作るべきか判断する

**作る:**

- その技法が自明ではなかった（自分が一度つまずいた）
- 別のプロジェクトでも同じ手順を参照したくなる
- 判断の分かれ目があり、文章で導く価値がある

**作らない:**

- 一度きりの解決策 → `ck note` に控える
- プロジェクト固有の規約・経緯 → `/doc-this` で `.claude/docs/` へ
- 正規表現や検査で機械的に強制できる制約 → `ck skill doctor` の検査を足す（`packages/ck/src/cli/commands/skill.ts`）。**文章での注意喚起より検査のほうが確実に効く**
- **複数スキルで同じ壊れ方を直した** → 直した形を文章で広めるのではなく、`skill.ts` の `BROKEN_PATTERNS`（旧パターンの再発を error）か `SHARED_SNIPPETS`（複製コード片のズレを error）に登録する。今回直した箇所以外に同じ旧パターンが残っていないかを doctor に探させる
- 既存スキルに 1 節足せば済む内容 → 新設せず改訂する（スキルの数は導線の複雑さに直結する）

## claude-kit の構成

1 スキル = 2 ファイル。メタデータはスタブに一本化し、本体には置かない。

```
packages/ck/src/skills/<name>/body.md      # 本体（フロントマターを書かない）
plugins/ck/skills/<name>/SKILL.md          # スタブ（フロントマター＋呼び出し行のみ）
```

スタブの形は全スキル共通:

```markdown
---
name: <name>                  # ディレクトリ名と一致させる
description: <どんなときに使うか>。「〜と言われたとき」を含めると起動判断が安定する
user-invocable: true
allowed-tools: <body が実際に使うツール>
argument-hint: "[任意: 引数の説明]"
---

!`ck skill print <name> || echo "ERROR: ck not found. Fix: cd ~/claude-kit && bun link"`
```

`||` のフォールバックは**バッククォートの内側**に置く（外に出すとシェルで実行されず doctor がエラーにする）。

## body の規約

- **フロントマターを書かない**（doctor がエラーにする）
- 必須の定型節を持つ: `## 非対話実行時` と `## 完了条件`
- 他スキルの参照は `` `/<name>` `` 記法で書く（この記法が導線グラフの実体になる）
- 冒頭に「位置づけ」と「コア原則」を置き、どのフェーズのスキルかを明示する
- 秘匿情報ガード: 実在の顧客名・案件名・認証情報・社内 URL を例示に使わない。外部に出る文字列（コミットメッセージ・PR 本文・Issue）を生成するスキルには、一般化して書く旨の制約を明記する
- `allowed-tools` に裸の `Bash` を置けるのは、プロジェクト固有のビルド・テストコマンドを実行する実装系スキルだけ。それ以外は `Bash(git:*)` のようにスコープを指定する（例外は `skill.ts` の `BARE_BASH_ALLOWED` に列挙する）

## Step 1: 書く前に、無い状態の挙動を見る

**スキルを書く前に、そのスキル無しで同じ状況に置かれたときにどう振る舞うかを確認する。** これがベースラインになる。

- 手元で似た状況を再現する、または `/fanout` の要領でサブエージェントを起動し、スキル無しで同じ課題を与える
- どこで判断を誤るか、どんな言い訳で手順を飛ばすかを**そのまま記録する**

この観察を飛ばすと、「正しそうだが誰も踏み外さない箇所」を丁寧に書き、「実際に踏み外す箇所」が抜けたスキルになる。

## Step 2: 観察した逸脱に対して書く

Step 1 で記録した逸脱を、そのまま節にする。

- 実際に出た言い訳は「Red Flags — STOP」や「言い訳と現実」の表に**原文に近い形で**入れる。抽象化すると効かなくなる
- 判断の分かれ目は表で示す（「こういうときは A、こういうときは B」）
- 手順は番号付きで、実行できる粒度まで落とす。コマンドは実際に動く形で書く
- 長い参考情報（API 仕様・一覧表）は本文に詰め込まず、別ファイルに分ける

## Step 3: 導線をつなぐ

**どのスキルからも参照されないスキルは、存在を忘れられる。** doctor は被参照ゼロを警告する。

- 新しいスキルを呼ぶべき場面を持つ既存スキルを特定し、そのスキルの該当ステップに `` `/<name>` `` の 1 行を足す
- 逆に、新しいスキルの出口（`## 完了条件`）から次のスキルを案内する
- `CLAUDE.md` のスキル優先関係にも追記が要るか確認する

## Step 4: 検査して確かめる

```bash
ck skill doctor          # スタブと本体の整合・定型節・リンク死活・裸 Bash・被参照
bun test                 # 実リポジトリ回帰テストが全スキルを走査する
ck skill print <name>    # 実際に出力される本文を目で確認する
```

doctor の警告（`⚠`）は exit 0 だが放置しない。エラー（`✗`）は exit 1 で、必ず解消する。

改訂した場合は、その節が**元々どの逸脱を防いでいたか**を確認してから削る。効いている歯止めを「冗長だから」と外さない。

## Red Flags — STOP

- 「今回こう解決した」という経緯をそのまま書こうとしている → 次の人が従える手順に書き換える
- スキル無しの挙動を見ずに書き始めている → Step 1 に戻る
- 機械的に検査できる制約を文章で書こうとしている → doctor の検査に落とす
- 既存スキルの 1 節で済む内容を新スキルにしようとしている → 改訂で済ませる
- 実在の顧客名・案件名を例示に使おうとしている → 一般化した例に置き換える

## 非対話実行時

スキルの新規作成・改訂は起動自体を承認とみなして進めてよい。ただし次を守る。

- Step 1 のベースライン観察を省略した場合、その旨を「本来確認すべきだった点」として報告する（省略自体は非対話では許容する）
- 既存スキルの**削除**と、既存スキルの規約（定型節・記法）の変更は非対話で行わない。提案にとどめて停止する
- `ck skill doctor` と `bun test` は非対話でも必ず実行し、結果を証跡として報告する（`/verify`）

## 完了条件

`ck skill doctor` がエラー 0 件で通り、`bun test` が緑で、新しいスキルが既存スキルから 1 箇所以上参照されている状態。完了後は `/commit` で論理単位のコミットに分割する。
