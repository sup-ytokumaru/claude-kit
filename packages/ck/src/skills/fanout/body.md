# fanout

互いに独立した複数の作業を、**サブエージェントに分けて並列で進める**ためのスキル。逐次に調べれば待ち時間が積み上がる作業を、1回の応答で同時に走らせる。

**位置づけ**: `/debug` で独立した複数の失敗が見つかったとき、`/qa` の観点別調査、`/review-others` の広いコードベース走査など、「分担できると分かったあと」の配分フェーズ。分担できるかどうかの見極めもこのスキルの前半で行う。

**コア原則: 1エージェント = 1つの独立した問題領域。文脈は継承させず、必要なものだけを渡して組み立てる。**

サブエージェントは自分の会話履歴を引き継がない。だからこそ、渡す指示の精度がそのまま成果の精度になる。同時に、調査の生ログが手元の文脈を埋めないという利点がある。

## Step 1: 分担できるか見極める

次のすべてを満たすときだけ並列化する。

- 問題領域が 2 つ以上ある（テストファイル別・サブシステム別・観点別）
- **それぞれが他の文脈なしで理解できる**
- 共有状態がない（同じファイルを書き換え合わない・同じポートや DB を奪い合わない）

ひとつでも欠けるなら並列にしない。次の場合は単一のエージェント、または自分で進める。

| 状況 | 理由 |
|---|---|
| 失敗どうしが関連している | 1つ直せば他も直る可能性がある。まとめて調べる |
| 全体像の把握が要る | 分割すると誰も全体を見ない |
| 何が壊れているかまだ不明 | 探索段階では分割の軸が決まらない |
| 同じファイルを触る | 編集が衝突する |
| 手順が前後に依存する | 逐次実行が必要 |

## Step 2: 領域を切り分ける

「何が壊れているか」でグルーピングし、各領域に名前をつける。切り分けた軸を宣言してから配分する（軸が言語化できないなら、まだ分割できていない）。

```
領域 A: 認証フローのテスト失敗 3 件
領域 B: 集計クエリのテスト失敗 2 件
領域 C: 画面遷移の E2E 失敗 1 件
```

## Step 3: 指示を組み立てる

各エージェントに渡すものは 4 つ。

1. **範囲** — 対象のファイル・サブシステムを名指しする（「全部直して」は迷子になる）
2. **文脈** — エラーメッセージ・テスト名・再現手順をそのまま貼る（こちらの会話は見えない）
3. **制約** — 触ってよい範囲と、触ってはいけない範囲（「本番コードは変更しない」等）
4. **返してほしい出力** — 何を報告させるか（根本原因・変更点・残課題）

```markdown
src/features/claim/claim.test.ts の失敗 3 件を調査して直す。

失敗内容:
- "承認済みの請求は再申請できない" — 期待 403 / 実際 200
- ...

やること:
1. テストを読み、各ケースが何を検証しているか把握する
2. 根本原因を特定する（タイミングの問題か、実装のバグか）
3. 原因に応じて修正する

制約: このテストファイルと対応する実装以外は変更しない。
返すもの: 根本原因と、変更したファイル・箇所の要約。
```

## Step 4: 並列で起動する

**1つの応答の中で、すべてのエージェント呼び出しを同時に発行する**。応答を分けて1つずつ呼ぶと逐次実行になり、並列化の意味がなくなる。

作業ツリーを奪い合う編集タスクでは、Claude Code 組み込みの `isolation: worktree` を使ってエージェントごとに独立した作業コピーを与える（ck では worktree 管理に専用の仕組みを持たず、組み込み機能に委ねる）。読み取り専用の調査なら分離は不要。

配分の目安:

- 調査・探索が中心 → 読み取り専用のエージェントで十分
- ファイル編集を伴う → `isolation: worktree` で分離するか、担当ファイルを完全に分ける
- 3〜4 領域を超える → 本当に独立か再点検する。多すぎる分割は統合コストに負ける

## Step 5: 統合して検証する

エージェントの成功報告は**証跡ではない**。戻ってきたら必ず次を行う。

1. 各要約を読み、何が変わったかを把握する
2. `git diff` で実際の変更を確認する（報告と差分が食い違うことがある）
3. 変更どうしが衝突していないか確認する
4. **テストスイート全体を通す**（個別に緑でも、合わせると赤になることがある）
5. `/verify` のゲートを通してから完了を報告する

系統的な誤り（全エージェントが同じ勘違いをする）が起きうるため、抜き取りで中身も確認する。

## よくある失敗

| 失敗 | 直し方 |
|---|---|
| 範囲が広すぎる（「テストを全部直して」） | 1ファイル・1サブシステムに絞る |
| 文脈が無い（「あの競合状態を直して」） | エラー文とテスト名を貼る |
| 制約が無い | 「本番コードは変更しない」等を明示する |
| 出力の指定が無い | 何を報告させるかを書く |
| 報告を検証せずに統合する | `git diff` と全体テストで裏を取る |
| 依存のある作業を並列化した | 逐次に戻す |

## 非対話実行時

領域の切り分けと配分は推奨案で進めてよい。ただし次を守る。

- 分割の軸と、各エージェントに与えた範囲・制約を最終報告に列挙する
- エージェントの報告をそのまま結論にせず、非対話でも `git diff` と全体テストで裏を取る（`/verify`）
- 判断が割れた領域（本当に独立か怪しい領域）は並列化せず、逐次で扱ったことを報告する

## 完了条件

全エージェントの結果が統合され、`git diff` で実際の変更を確認したうえで、テストスイート全体が通っている状態。衝突や未解決の領域が残る場合は、並列化の失敗として明示的に報告する。
